# Features

The state of every feature: its stage, what it promises, what proves it and what the owner has approved. One file per feature, `<slug>.yaml`; the map below is generated from them.

The rules behind the fields are in [Feature stages](../process/feature-stages.md), [Testing](../process/testing.md) and [Review](../process/review.md).

## A feature is its slug

A feature is a capability of the platform, such as `tenant-suspend` or `gateway-auth`, named by a short kebab-case slug. The slug is the file name and the key everything else uses: tests (`// Verifies: tenant-suspend AC-2; T-01`), release flags ([ADR-0011](../adr/0011-feature-flags.md)), the QS runs log and the skills.

Linear issues are the work on a feature: one issue takes it to `alpha`, a later "Stabilize" issue takes it to `stable`. The file lists them under `links`, and each issue links back to the file. The links are for people. No tool and no gate reads Linear: if Linear is gone, the state of every feature is still here.

## The map

Generated by `tools/featuremap` from the files in this folder; do not edit it by hand. Run `go -C tools/featuremap run .` after changing a feature file. CI fails when the map is out of date.

**Stage** is the last stage `feature-verify` reported Ready for. A `stable` feature whose code changed after its last review shows as `beta` until the owner reads the delta. **Gaps** are what stands between the feature and its target: missing acceptance criteria or approvals, and the failed and not-checked items of the latest verify run. **critical** marks features where a bug leaks data between tenants or loses usage.

The features of the platform skeleton start at `beta` without a verify run: `HAMSP-23-platform-skeleton` is merged at `beta` by decision ([Roadmap](../roadmap.md)). Their gaps stay visible until each one is verified and stabilized.

## File format

```yaml
feature: tenant-suspend             # the slug, equal to the file name
title: Suspend a tenant
target: beta                        # the stage the current work aims at
stage: alpha                        # the last stage feature-verify reported Ready for; omitted before that
critical: false                     # true: a bug here leaks data between tenants or loses usage
flag: tenant-suspend                # its release flag, if it has one
code:                               # the code this feature owns, as globs from the repo root
  - apps/gateway/suspend/**
c4: [apiGateway]                    # optional: element names in docs/architecture/c4/workspace.dsl
links:                              # informational only
  issues: [HAMSP-52]
requirements: [FR-01, QS-03]        # the FR, QS and C items the feature touches

acceptance:                         # gate G-02; written by feature-clarify
  AC-1:
    text: A request of a suspended tenant gets 403 at the API Gateway.
    level: integration
    planned: apps/gateway/suspend/suspend_test.go:TestSuspendedTenantGets403   # feature-plan
    verified: [apps/gateway/suspend/suspend_test.go:TestSuspendedTenantGets403] # feature-verify

checklist:                          # gate G-04; Testing, sections 4 and 5
  T-01:
    planned: applies — a token of tenant B on a suspended tenant A's record; gateway and ExampleApp
    verified: [apps/gateway/suspend/suspend_test.go:TestSuspendedTenantForeignToken]
  T-08:
    planned: does not apply — no migration
    verified: n/a — no migration in the diff

quality_scenarios:                  # gate G-05; Testing, section 7
  touched: [QS-03]
  tests:                            # cheap QS tests, counted like ACs
    QS-03:
      planned: prototype/e2e/ratelimit_test.go:TestNoisyTenantLowLoad
  recommended_runs: [QS-03 on kind, k6 noisy tenant]

plan_approved: 2026-11-12           # gate G-07; cleared when target changes
structure_approved: null            # gate G-08
reviews:                            # gate G-06, newest last
  - date: 2027-02-01
    commit: 1a2b3c4d
    scope: full                     # full | delta

deviations: []                      # approved "applies" that became n/a, each with the owner's approval date
runs:                               # one entry per feature-verify run, newest last
  - date: 2026-11-20
    commit: 1a2b3c4d
    stage_checked: alpha
    verdict: ready                  # ready | not-ready
    failed: []
    not_checked: [G-01]
```

### Who writes what

| Field | Written by |
|---|---|
| `feature`, `title`, `target`, `acceptance.*.text`, `requirements`, `links` | `feature-clarify` |
| `code`, `flag`, `critical`, `c4`, the `planned` entries, `quality_scenarios.touched` | `feature-plan` |
| `plan_approved`, `structure_approved`, `reviews`, `deviations` approvals | The owner, in chat; the agent writes the line. |
| `stage`, the `verified` entries, `recommended_runs`, `runs` | `feature-verify` |

`code` globs may overlap: a file can belong to two features, and a change to it counts for both. A file that belongs to no feature is allowed.

A `verified` entry is either a list of tests as `path:TestName` or `n/a — <reason>`. CI checks that each listed test exists and has a `// Verifies:` comment that names the feature and the ID.
